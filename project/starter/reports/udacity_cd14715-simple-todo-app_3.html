Quality issues (10)

  • Line 17 · critical · security

    PaymentDetails carries the full card number into application code, alongside a CVV field (line 19). Processing raw card credentials directly expands the application?s PCI scope; use a payment-provider token or hosted payment flow and never persist or log the full number or CVV.

    Suggested fix: Use a provider-supported idempotent payment workflow and a durable transaction/compensation strategy so a failed subscription update is reconciled or the payment is reversed.

    Card-number validation accepts only a length of 16. Valid card numbers can have different lengths, and length alone does not establish a valid number.

    Suggested fix: Delegate card validation to the payment provider; if the application must validate a number, support the provider?s card formats and use a vetted validation routine.

    Suggested fix: Prefer tokenized provider input. If accepting a card number here, reject non-digit input before any processing.

    Suggested fix: Avoid collecting CVV in application code; otherwise validate the provider-supported numeric format and never store or log the value.
